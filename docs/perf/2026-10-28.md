# Performance pass, 2026-10-28

Run with the `performance` skill (daveebbelaar/bama), adapted to iOS. All numbers
are from optimized (Release) builds on an iPhone 18 Pro simulator (iOS 27) with
1,000 brews over 30 beans (`-perfBrews 1000`, in-memory store). Other work was
running on the Mac at the same time, so wall-clock times are noisy; CPU
instructions retired by the app is the steadiest number and is what the claims
below use.

## How to rerun

```bash
touch docs/perf/.measure
xcodebuild -project NextCup.xcodeproj -scheme NextCup -configuration Release \
  -destination 'platform=iOS Simulator,name=iPhone 18 Pro' \
  SWIFT_ACTIVE_COMPILATION_CONDITIONS=DEBUG ENABLE_TESTABILITY=YES \
  -only-testing:NextCupUITests/PerformanceUITests test
rm docs/perf/.measure
```

`SWIFT_ACTIVE_COMPILATION_CONDITIONS=DEBUG` keeps the debug-only `-perfBrews`
seed in an optimized build.

## Whole-app flows (PerformanceUITests, mean of 5)

| Flow | Before | After | Change |
| --- | --- | --- | --- |
| Journal search: type "juicy", wait for a match, erase | 8.11 G instr | 7.01 G instr | −14% |
| Explore tab and back to Journal | 6.08 G instr | 5.63 G instr | −7% |
| Journal scroll: 4 flicks down, 4 up | 9.52 G instr | 10.08 G instr | noise (RSD 7%) |
| Launch to first responsive frame | 5.6 s | 5.4 s | noise (seeding dominates) |

These include XCUITest's own accessibility queries, which the app pays for, so
the app's share of each flow is larger than the percentages show.

## Hot paths (release micro-benchmarks, median of 15)

| Work | Before | After |
| --- | --- | --- |
| Explore recommendation history (`ExploreModel.history`) | 7.9 ms | 4.7 ms |
| Journal list work per update (modeled: list, bean names, filter) | about 5.3 ms | about 1.6 ms |
| Journal list work per search keystroke (same, with search) | about 9.5 ms | about 5.7 ms |
| Daily backup archive build (`DataExporter.archive`) | 169 ms | 145 ms |

The Journal rows are modeled from measured parts: before, each update built
the brew list 4 times and the bean names 3 times; now once each.

## What the profile showed

Time Profiler (`xctrace`, text export) while switching tabs and scrolling: the
top app frames were `ExploreModel.history`, mostly mapping the same bean through
the flavor taxonomy once per brew, then faulting `BrewBean.bean` one row at a
time. Scrolling the journal is almost all SwiftUI and UIKit list work; no app
frame stood out, so nothing there was changed.

## Tried and dropped

- Prefetching each brew's bean parts in the Journal and Explore queries: no
  gain (Explore 5.51 → 5.65 G instr).
- Reading sort keys once in `JournalFilter`: the newest-first sort got slower
  (0.56 → 0.69 ms).
- A predicate-based generic `Store.find`: 20× faster lookups, but the generic
  `#Predicate` traps in release builds. See the architecture review.

## Already fine

- The brew timer publishes to the view once a second, not on every 250 ms tick.
- Hero photos are 1600 × 1066 JPEGs from the asset catalog (system-cached).
